## 6. Code Quality Observations

### Strengths

1. **Analytics decoupled from UI**: Widgets expose `onShown` callbacks, caller owns event emission — keeps design-system components free of observability imports.
2. **Error codes exhaustive**: `teCodeFor` uses Dart 3.0 switch expressions to guarantee coverage of all `Failure` subtypes.
3. **Failure-to-code mapping centralized**: Single source of truth in `error_te_code.dart` — no copy-paste risk.
4. **Test helpers clear**: `RecordingAnalytics` captures events in order for direct assertion on `name`/`parameters` — no matcher-based indirection.
5. **Documentation thorough**: All events have §-numbered plan references; error codes map to PRD TE codes.

### Minor Notes (Not blockers)

1. **Recording fake pattern**: Both `RecordingAnalytics` and `RecordingErrorReporter` follow the "capture everything in a list" pattern — standard and effective, but slightly verbose. Not a code smell; just a style note.
2. **onShown callback pattern**: Three different error widgets (`OfflineErrorWidget`, `GenericErrorWidget`, `StaleCacheBanner`) each define their own `onShown` callback rather than a shared base. This is intentional (each error has its own TE code), and the pattern is clear. No simplification needed.
